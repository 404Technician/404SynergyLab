# General mechanic rules (v0.9.0)

The rule explorer works alongside the curated build experiments. It evaluates the selected source record on demand; it does not brute-force every multi-skill/multi-item build or claim that all mechanics are understood.

| --- | --- | --- |

| Support profiles | 567 | Required/excluded type expressions, added types, context flags and selected harmful restrictions |

Structured types are not a complete model of a skill or support. Partial item profiles also retain an explicit unknown-modifier warning. No record is silently treated as fully understood.

## Rules and constraints

A support check evaluates the recorded base predicates. Exclusions and cannot-be-supported flags reject the base route. Minion types remain separate; potential minion routes and special/added-type contexts remain unknown. Source matches are not advice to assign a support. In particular, Brutality and Controlled Destruction retain their damage/critical-hit restriction warnings.

A conversion link requires a damage-capable base skill with a matching source type hint. It is explicitly conditional on actual outgoing player damage. Player conversion is not transferred to minion damage. Other conversions, extra damage, ailment application, weapon/slot requirements, numerical damage and resource constraints are not simulated.

Granted-skill and trigger links resolve literal skill names to catalog references. If several records share a name, the result asks for exact effect/variant verification. A granted skill is a source relationship rather than proof of synergy. Explicit item triggers require the recorded event, with cooldown, cost and frequency left unverified.

Source variant tags remain required conditions; a historical modifier is not silently treated as current. Incoming/parry-specific conversion and other unrecognized grammar are not forced into the player conversion model. Dynamic unique modifier generators are not executed.

The setup checkboxes explicitly state no elemental damage, no Chaos damage or no critical hits. They block only the represented destination component or critical trigger. They do not declare the whole build invalid; unrelated damage components and events may still function.

## Provenance and updates

`data/mechanics/manifest.json` pins the profile ID, rule version, source revision and full catalog ID. All input source-file fingerprints must match the reference catalog. Normalized source records and recognized item lines retain their hashes and immutable links. Descriptions and full stat tables are not copied.

```powershell
npm run mechanics:import -- ../PathOfBuilding-PoE2 --check
```

The source checkout must be at the declared revision. Without `--check`, the command regenerates the profile snapshot. CI compares exact generated bytes. Browser builds bind the snapshot to its hash; URLs preserve the mechanics ID and setup restrictions. Missing historical profiles show an error instead of changing rules silently.

New source revisions require a new snapshot ID and coverage review. Changes to rule meaning require a new rule/profile version. Future mechanics can add explicit producers, requirements, consumers and actor scopes, followed by bounded multi-step chains and conflict checks. Until those rules exist, they remain unknown.
